CORRECTION 1 — ssh_sudo_capture replaced completely
--------------------------------------------------------------------------------
Old defect: the inner command was embedded so that sort ran inside/alongside
the Docker command substitution and a quoted command string could be treated
as one executable; a failed query could still emit NONE.

New implementation (scripts/run-phase-b-deploy.sh, ssh_sudo_capture):
  - The inner command is interpolated as a plain shell command line inside
    the remote script — never quoted as a single executable.
  - The remote block runs:  out=$( <inner> 2>err ); rc=$?  under set +e
    guards, so the capture happens FIRST and the exact status is read.
  - On rc != 0 the remote block prints a diagnostic to stderr and exits with
    the SAME rc. NONE is never emitted on failure.
  - sort runs ONLY in the success branch, after the empty/non-empty check,
    and never inside the command substitution.
  - Locally, return "${PIPESTATUS[0]}" preserves the remote nonzero status
    across the local `| tee evidence-file` pipeline.

Tests (test_ssh_sudo_capture.sh) execute the EXACT generated remote command
(the mock SSH transport logs the command string verbatim and runs it with
bash -c against PATH-shimmed sudo/docker mocks):
  a. successful empty output      -> rc 0, output exactly NONE
  b. successful nonempty output   -> rc 0, output sorted (def/abc/ghi ->
                                     abc/def/ghi)
  c. sudo failure (exit 42)       -> function returns exactly 42 AFTER the
                                     local tee pipeline; no NONE emitted
  d. Docker failure (exit 17)     -> function returns exactly 17 AFTER the
                                     local tee pipeline; no NONE emitted
Structural assertions on the generated command: begins with
set -Eeuo pipefail; no sort/pipeline inside the $() substitution; inner
command not quoted as a single executable; sort occurs only after the rc
check; all 4 generated commands begin with set -Eeuo pipefail.

CORRECTION 3 — Stage-aware rollback
--------------------------------------------------------------------------------
- Gate 2's FIRST remote command is a READ-ONLY existing-resource check
  (containers, container names, volumes, networks, orchestrator image,
  /opt/hada tree, hada-supervisor unit). It runs BEFORE the remote temp dir
  is created and before any upload. Pre-existing HADA resources cause
  immediate refusal with zero mutation.
- Remote temp-dir creation moved to the END of Gate 2 (first mutation, after
  every read-only verification).
- This run's resources are tracked (CREATED_CONTAINERS/VOLUMES/NETWORKS/
  IMAGES, UNIT_INSTALLED, SUPERVISOR_STARTED, COMPOSE_UP_DONE).
- bounded_rollback() stops the supervisor ONLY if SUPERVISOR_STARTED=1,
  composes down (never -v) ONLY if COMPOSE_UP_DONE=1 with tracked
  containers, removes the unit ONLY if UNIT_INSTALLED=1. It never deletes
  /var/lib/hada or /opt/hada.
- main() calls NO rollback after a Gate 2 refusal or initial-state failure
  ("ABORT: Gate 2 failed (zero mutation, zero rollback)").

Mocked tests (test_stage_aware_rollback.sh) prove:
  - existing-resource scenario: refusal (rc!=0), EXACTLY ONE remote command
    issued (the read-only check), zero mutation/rollback commands in the
    decoded command log, REMOTE_DIR_CREATED remains 0;
  - clean scenario: the check is the first remote command; temp-dir creation
    is the final Gate 2 step;
  - bounded_rollback with nothing tracked issues ZERO remote commands;
  - bounded_rollback with tracked resources stops the supervisor, composes
    down WITHOUT -v, removes the unit, and never deletes persistent paths;
  - Gate-2-only progress (temp dir only) triggers no compose/service/unit
    rollback commands.

CORRECTION 4 — Remote-block discipline
--------------------------------------------------------------------------------
Every remote shell block generated by the runner begins with
set -Eeuo pipefail (verified per-command by the mocked tests, which decode
each transmitted command). All privileged commands use sudo -n. Multi-command
preparation blocks (create-dirs, stage-release, install-release) consist of
sequential install/cp/chown/mv/systemctl commands executing under
set -Eeuo pipefail with no `|| true` and no trailing echo: the first failing
install/mkdir/chown/chmod/cp/systemctl aborts the block and the block's exit
status is the failing command's status — a final echo can never mask an
earlier error (blocks that previously ended in "echo PASS" now end with the
last real command or a PASS message only in single-command report blocks).

CORRECTION 5 — Remote temporary material protection
--------------------------------------------------------------------------------
- Remote temp dir: created with `umask 077` + `install -d -m 0700`, then
  mode re-verified remotely (stat -c %a must equal 700, else the block
  fails).
- Resolved real-secret Compose JSON is NEVER stored on the remote host: the
  render command pipes `docker compose config --format json` to stdout and
  it is streamed over SSH directly into a LOCAL mktemp file created under
  umask 077 and chmod 0600, validated structurally (ports + volumes via
  python3), then deleted immediately (rm -f) in both success and failure
  paths.
Tests (test_remote_temp_permissions.sh) execute the exact generated
temp-dir command in a sandbox and stat the result (700, drwx------), prove
umask 077 precedes creation, prove the render leaves no
effective-compose*.json behind, prove the 0600 temp pattern, and statically
prove the remote render block contains no remote JSON persistence and the
runner has no world-readable JSON permission pattern.

CORRECTION 6 — Secrets removed from process arguments
--------------------------------------------------------------------------------
The old check extracted VALKEY_PASSWORD on the host and passed it through
`exec -T -e VALKEYCLI_AUTH=<value>` — the secret appeared in the host
command line. Replaced with an entirely in-container check:

  ... exec -T valkey sh -c
      'VALKEYCLI_AUTH="${VALKEY_PASSWORD:?...}" valkey-cli ping'

The single-quoted sh -c body is expanded INSIDE the container from the
container's own VALKEY_PASSWORD environment. No `valkey-cli -a` anywhere; the
secret never appears in the host command line, the runner log, or evidence
(evidence records only the command template and PONG/health markers).

elsewhere — both fail closed.
