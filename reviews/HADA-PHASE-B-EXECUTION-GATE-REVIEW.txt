4. SECURITY REVIEW — DEPLOYMENT-TIME IMPLICATIONS
============================================================

node-exporter (pid: host + /:/host:ro,rslave)
  - Grants visibility into host PID namespace AND the entire host filesystem.
  - rslave ensures mount propagation is slave (no mount leaks to host).
  - ro ensures filesystem reads cannot mutate host state.
  - Acceptance: read-only host metrics require these; risk is broad host
    filesystem read. Mitigate by ensuring cap_drop ALL, no-new-privileges,
    and no docker socket mount.

alloy (reads /var/lib/docker/containers:ro)
  - Reads container log JSON files to scrape logs. Read-only bind is
    appropriate; limited blast radius.
  - Risk: if /var/lib/docker/containers is replaced with a symlink or mount,
    alloy could escape. Mitigate: do not mount docker socket, rootfs read-only.

orchestrator (writable /var/lib/hada)
  - Holds evidence, keys, workspaces, repositories, and app state.
  - Writable access to /var/lib/hada is required for durability.
  - Runs as UID 10001 (hada), with overlay read-only rootfs and tmpfs for
    /tmp and /var/log/hada. Acceptable for the threat model.

caddy (NET_BIND_SERVICE)
  - Caddy image runs as root in the base; NET_BIND_SERVICE is therefore
    redundant but not harmful. Confirm no other cap_add entries exist.
  - Only port 80 is published; port 443 is absent. Admin interface is off.
  - Acceptable.

postgres / valkey cap_add requirements
  - CHOWN, DAC_OVERRIDE, FOWNER, SETGID, SETUID needed for first-run
    volume ownership fixup at container start.
  - Combined with cap_drop ALL on baseline, this limits privilege to only
    the required operations.
  - Pre-chowning volumes in Gate 3a may allow dropping SETUID/SETGID at
    runtime in a future phase; current set is acceptable for Phase B.

7. GATE 0 FINDINGS (REVIEWER FLAGS — NOT DEPLOYMENT BLOCKERS)
============================================================
The runner is fail-closed and refused to proceed. Three Gate 0 defects
were found. These are runner-quality issues, not issues with the target
infrastructure, the candidate, or the Phase B0 preflight.

FINDING-1: shellcheck Gate 0b — SC2016 info-level findings in
           validate-host.gcp.sh (false positive on bash -c wrapper)
  Lines affected: 26, 31, 32, 33
  Nature: The script uses `bash -c '... $(command) ...'` intentionally.
  shellcheck SC2016 warns that expressions don't expand inside single-quoted
  strings. These are blank lines handed to bash -c; the shellcheck
  invocation runs at the LOCAL machine's shellcheck, not the remote one.
  Effect: shellcheck exits 0 but prints informational warnings; runner Gate
  0b misinterprets any shellcheck output as a failure.
  Severity: LOW — the script works correctly on the remote shell.
  Resolution: Gate 0b should invoke shellcheck with `-S error` (as the
  strict check already does) so informational warnings do not trip the gate.

FINDING-2: Secret-redaction Gate 0g — false positives on legitimate VAR
           references and redaction placeholders
  Lines/scripts affected:
    scripts/provision-secrets.sh — lines 61, 62, 64, 42, 43, 68, 69
    scripts/run-phase-b0-preflight.sh — line 343 (HADA_DATABASE_DSN=...***...)
    scripts/run-phase-b-deploy.sh — line 790 (VALKEY_PASSWORD=*** inside
      grep pipeline inside a remote-command heredoc)
  Nature: The case-statement on line 313 includes `\\$\\{*` which never
  matches a real `${VAR}` expansion because `\$` is a literal backslash-
  dollar in that context, not the start of parameter expansion. As a
  result, lines like `POSTGRES_PASSWORD=${POSTGRES_PASSWORD}` and
  `HADA_DATABASE_DSN="postgresql://${POSTGRES_USER}:***@..."` are
  flagged as potential literal secrets. Line 790's `VALKEY_PASSWORD=***`
  is the legitimate redaction placeholder and should not be flagged.
  Severity: MEDIUM — this is a real regex bug. A reviewer who fixes this
  check must ensure both `${VAR}` RHS lines AND the `***` placeholder
  continue to pass without suppression.
  Resolution: The escape sequence in the case pattern must match actual
  bash parameter expansion syntax. The correct form is `${*}` not `\$\{*`;
  the leading backslash before `$` makes it a literal.

FINDING-3: Cleanup/rollback guard Gate 0h — grep for remote-dir pattern
           in self does not match actual literal
  Lines: 167, 171-173 in cleanup()
  Nature: Gate 0h greps the script for the literal `hada-b-deploy-[0-9]`
  but the actual lint target is `hada-b-deploy-${TIMESTAMP}` which is
  interpolated at runtime. The guard that matters is the regex at line
  171: `^/tmp/hada-b-deploy-[0-9]+$` which IS present and correct.
  Severity: LOW — the functional guard is correct; only the static
  self-test grep is wrong.
  Resolution: Gate 0h self-check should grep for `hada-b-deploy-id: this is last block}}}}` or the actual regex literal
  `^/tmp/hada-b-deploy-[0-9]` rather than a partial form.
